# Создание USW flow

Создать или обновить один человекочитаемый Markdown flow. Не выполнять его.

## Диалог

Обсуждать свободно, без фиксированного меню. Предлагать один выбор за раз и
явно называть разрешаемое действие. Варианты ответа — отдельным блоком в конце
сообщения с номерами `1.`, `2.`, `3.`; пункты пояснения — `A`, `B`, `A1`,
`A.1`. Нумерацию шагов flow внутри черновика или диффа сохранять. Принимать
ответ числом или свободным текстом; для самостоятельного ввода варианты
необязательны. Выбор темы обсуждения не разрешает запись.

## Разбор запроса

1. Разобрать два независимых необязательных селектора, каждый — не более одного раза:
   - origin: `--local` или `-l` выбирает `<project>/.usw/flows`;
     `--shared` выбирает безопасно настроенный `flows.root`;
     без селектора использовать общий;
   - стиль: `--structured` или `-s` выбирает `version-2`.
2. Повторённый, конфликтующий или неизвестный селектор отклонить.
3. С селектором стиля полностью прочитать
   [references/version-2.md](references/version-2.md). Без него этот файл не
   читать и создавать новый flow как обычный Markdown.
4. Потребовать одно безопасное kebab-case имя.

## Проектирование от цели

Если по правилам выбора точки входа ниже flow новый и пользователь не передал
`--structured` или `-s`, перед первым черновиком один раз сообщить:

> По умолчанию я создам обычный Markdown flow. Для сложных процессов доступен
> режим `--structured` (`-s`) — нотация `version-2` с явными вызовами,
> развилками, циклами и параллельными шагами (`CALL`, `GATE`, `LOOP`,
> `PARALLEL`). Это подсказки для модели, а не исполняемый язык. Если не
> попросите иначе, продолжу в обычном формате.

Не ждать ответа и продолжить обычный Markdown. Для существующего flow или явно
выбранного стиля подсказку не показывать. Если пользователь до записи просит
переключиться, прочитать `references/version-2.md` и заново показать черновик в
`version-2`.

Если пользователь описал цель, а не готовые шаги:

1. Прочитать каталог рецептов [references/recipes.md](references/recipes.md).
2. Предложить черновик: линейные нумерованные шаги основного пути,
   без структурных маркеров сверх необходимого.
3. Назвать применимые по условиям каталога блоки — только те, что реально
   нужны этой цели, каждый с одним предложением почему.
4. Согласовать структуру с пользователем до записи. Для согласованных блоков
   прочитать их файлы из `references/recipes/` и встроить блоки в текст flow
   при записи; отклонённые блоки не встраивать.

Простой линейный flow исполняется надёжнее структурного. Добавлять `GATE`,
`LOOP` и `PARALLEL` только когда без них разные исходы неразличимы.

## Выбор точки входа

1. Проверить два кандидата: `<flow-root>/<name>.md` и
   `<flow-root>/<name>/FLOW.md`.
2. Существуют оба — остановиться с `ambiguous_flow_layout`.
3. Существует ровно один — редактировать его. Сначала прочитать текущий текст;
   без явной просьбы сменить стиль сохранить его форму — обычную или
   `version-2` — и не перемещать flow между раскладками.
4. Не существует ни одного — создать `<flow-root>/<name>/FLOW.md`. Безопасную
   существующую директорию `<name>` без `FLOW.md` использовать как пакет.

## Безопасность записи

- Изменять только выбранную точку входа. Соседние ресурсы пакета не читать
  и не изменять.
- Отклонить выход за пределы каталога, symlink и неожиданный тип файла в
  корне, пакете и точке входа. Непосредственно перед записью повторить эту
  проверку по обоим кандидатам; если появилась вторая раскладка, цель
  изменилась или стала symlink — остановиться без записи.
- Если разные толкования текста меняют действие, исполнителя или внешний
  эффект — задать вопрос до записи.
- Flow не предоставляет полномочий на внешние или разрушающие действия.

## Сигналы сложности

Проверить текст flow перед записью и при проектном разборе. Сложный flow модельный
исполнитель может не исполнить: он теряет позицию и толкует ветки по-разному.
Сигналы:

- больше ~12 шагов на одном уровне — предложить разбить на два flow;
- `GATE` с более чем 4 ветками — предложить объединить исходы;
- `LOOP` внутри `LOOP`, либо `LOOP`, содержащий `PARALLEL` или вызов другого
  flow, — предложить вынести внутреннюю часть в отдельный flow;
- `PARALLEL` с более чем 3 ветками или с зависимыми ветками — сократить или
  сделать последовательным;
- неявные переходы «вернуться к шагу N» между разделами — заменить явным
  `LOOP` с пределом.

При любом сигнале предупредить, что flow может исполниться ненадёжно,
предложить конкретное упрощение и рекомендовать после сохранения запустить
`$usw-assess-flow [--local|--shared] <name>`. Запись не блокировать: решение
остаётся за пользователем.

## Проверка и отчёт

1. Перечитать сохранённый UTF-8 файл. Убедиться, что процесс понятен и другие
   файлы не изменились.
2. Сообщить имя, origin, путь, стиль и точную команду запуска:
   `$usw-run-flow --local <name> <input>` либо
   `$usw-run-flow --shared <name> <input>`.

## Подсказки по проектированию

После отчёта провести один короткий проектный разбор только на чтение:

1. Прочитать каталог рецептов [references/recipes.md](references/recipes.md)
   и исключить рецепты, отклонённые при согласовании структуры текущего flow,
   в том числе из кратких рекомендаций. Из остальных выбрать по условиям
   каталога не более трёх наиболее релевантных рецептов.
   Пропуск записи подсказок после сохранения — другое решение: если пользователь
   просит показать scan без применения, подсказки всё равно показать.
   Сначала ранжировать пробелы безопасности и проверяемости результата. Если
   подходящих нет — коротко сказать об этом и завершить работу.
2. Прочитать только файлы выбранных рецептов из `references/recipes/`.
   Остальные применимые рецепты назвать одной строкой по каталогу, без
   детализации и без чтения их файлов.
3. Обозначить подсказки буквами `A`, `B`, `C`. Для каждой показать: что добавить,
   почему это полезно именно этому flow, готовую правку в текущем стиле
   в блоке `diff` с заголовками
   `---`/`+++`, путём entrypoint и контекстом сохранённого файла. Место правки
   определять по точному контексту и удаляемым строкам, без зависимости от
   номеров строк hunk; если место неоднозначно — уточнить до записи.

Продолжать доработку предложений по просьбам пользователя без лимита итераций.
Просьба сократить, переделать или обсудить без разрешения записать означает
новый preview диффом без записи. При ожидании ответа возвращать управление
пользователю.

Записывать только по явному указанию записать конкретную правку — словами либо
номером варианта, который явно предлагает эту запись. Неоднозначное согласие
уточнять. Без разрешения файл остаётся byte-for-byte неизменным; разрешение
одной revision не распространяется на следующую. Перед каждой записью прочитать
актуальный файл: если изменения базы меняют согласованную правку, показать
обновлённый дифф и получить новое разрешение. Непосредственно перед записью
повторить проверки из «Безопасность записи», сохранить origin, раскладку и
стиль, изменить только выбранный entrypoint и перечитать результат.

После первой revision проектный разбор повторно не запускать и новые рецепты
автоматически не предлагать; можно продолжать обсуждение прежних предложений.

Для обычного Markdown предлагать простой текст без структурных маркеров.
`CALL`, `GATE`, `LOOP` и `PARALLEL` предлагать только для `version-2`.
Contract tokens из рецептов, например `approve`, `change`, `cancel`, сохранять
дословно и при преобразовании в обычную прозу.

Точка возврата: после отчёта и проектного разбора, каждого preview с ожиданием
ответа либо разрешённой записи; flow не исполнять.
