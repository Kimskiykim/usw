# Создание USW flow

Создавать один понятный человеку Markdown-файл. По умолчанию не требовать
версию, DSL, постоянные action names или специальную структуру.

## Подготовка

1. Разобрать только два независимых optional selector:
   - `--local` или `-l` выбирает `<project>/.usw/flows`;
   - `--structured` или `-s` выбирает человекочитаемый `version-2` authoring
     style.
   Их можно сочетать; повторённый или неизвестный selector отклонить.
2. Со structured selector полностью прочитать
   [references/version-2.md](references/version-2.md).
   Без него не читать reference и создавать новый flow как ordinary Markdown.
3. Выбрать один root без fallback: local либо безопасный configured
   `flows.root`.
4. Потребовать безопасное kebab-case имя и regular `<name>.md`; отклонить
   traversal, symlink и другой filesystem type.
5. При редактировании сначала прочитать существующий flow. Без явной просьбы
   изменить style сохранить его ordinary или `version-2` форму.

## Создание и проверка

- Изменить только выбранный `<flow-root>/<name>.md` и не выполнять описанный flow.
- Если разные толкования меняют действие, исполнителя или внешний эффект,
  запросить недостающее решение до записи.
- Flow не предоставляет полномочия на внешние или destructive actions.
- Прочитать сохранённый UTF-8 Markdown и проверить понятность процесса и
  отсутствие непреднамеренных изменений других файлов.
- Сообщить имя, origin, путь, authoring style и точную команду:
  `$usw-run-flow --local <name> <input>` либо
  `$usw-run-flow --shared <name> <input>`.

## Подсказки по проектированию

После успешного сохранения и отчёта автоматически провести короткий read-only
design scan. Показать три наиболее релевантные подсказки или меньше, если
подходящих нет. Сначала ранжировать пробелы безопасности и проверяемости
результата, затем остальные конкретные улучшения. Не предлагать элементы ради
полноты или для гипотетической пользы.

Для каждой подсказки показать:

- что можно добавить;
- почему это полезно именно для этого flow;
- готовый фрагмент Markdown в текущем authoring style;
- варианты `применить`, `изменить` или `пропустить`.

Для ordinary Markdown предлагать обычный текст без structured markers.
Только для `version-2` можно предлагать применимые `CALL`, `GATE`, `LOOP` или
`PARALLEL`.

`применить` записывает только выбранный фрагмент. `изменить` сначала показывает
переработанный фрагмент без записи; для его записи пользователь должен отдельно
выбрать `применить`. `пропустить` ничего не изменяет. При записи использовать тот
же origin и сохранить authoring style, затем повторно прочитать и проверить
файл. После revision не запускать design scan повторно. Если полезных подсказок
нет, коротко сообщить об этом и завершить работу.

## Рецепты подсказок

Примеры в рецептах ниже показывают только `version-2` форму. Не копировать их
structured markers в ordinary flow. Для ordinary flow выдавать готовый
нумерованный фрагмент обычными фразами: «попросить человека», «если результат
такой — сделать это», «повторить не более N раз» или «провести независимые
проверки», без `CALL`, `GATE`, `LOOP` и `PARALLEL`.

### Проверка результата

Предлагать, когда flow создаёт результат, но не подтверждает его корректность.
Сначала добавить наблюдаемую проверку: test command, validation или review.
`GATE` предлагать только в `version-2` и только когда разные результаты проверки
требуют разных следующих действий:

```markdown
1. Выполнить `<проверку>`.
2. GATE результата:
   - проверка успешна → продолжить;
   - проверка неуспешна → вернуть на исправление;
   - проверить невозможно → вернуть `blocked`.
```

### Human decision

Предлагать только когда остаётся несколько допустимых вариантов, выбор меняет
следующее действие или внешний эффект и его нельзя вывести из уже заданных
критериев. Не считать отсутствие ответа согласием:

```markdown
1. CALL HUMAN `owner` и показать варианты с последствиями.
2. GATE решения:
   - `approve` → продолжить;
   - `change` → вернуть на доработку;
   - `cancel` → завершить без действия.
```

### Подтверждение внешнего действия

Предлагать только если сам flow действительно содержит deploy, release, push,
удаление, необратимую запись или другой существенный side effect и перед ним
ещё нет явного подтверждения:

```markdown
1. Показать точное действие, цель и ожидаемый эффект.
2. CALL HUMAN `owner`.
3. GATE разрешения:
   - подтверждено → выполнить действие;
   - отклонено → завершить без действия;
   - требуется изменение → вернуть на подготовку.
```

Flow не предоставляет полномочия сам по себе.

### Обработка ошибки

Предлагать только когда конкретный fallible step имеет значимый неуспешный
исход, требующий другого следующего действия, но flow описывает только happy
path:

```markdown
1. Выполнить действие.
2. GATE результата:
   - успешно → продолжить;
   - исправимая ошибка → вернуть на исправление;
   - внешний blocker → вернуть `blocked`;
   - неисправимая ошибка → вернуть `failed`.
```

Не придумывать automatic retry без доказанной безопасной повторяемости.

### Ограниченная доработка

Предлагать, когда результат может потребовать повторной проверки и исправления,
а повторяемые шаги read-only, идемпотентны или безопасно обратимы:

```markdown
LOOP не более `<предел>` попыток:
1. Подготовить или исправить результат.
2. Выполнить проверку.
3. Если критерий выполнен → выйти с `completed`.
4. Если предел исчерпан → вернуть `decision_required` или `failed`.
```

Всегда указывать критерий выхода и предел. Не предлагать бесконечный цикл.
Не помещать в цикл внешнюю запись или другой небезопасный повтор: циклически
дорабатывать и проверять подготовленный результат, а approval и внешнее действие
оставлять после выхода из цикла.

### Независимые проверки

Предлагать, когда несколько read-only проверок не зависят друг от друга и не
изменяют общий state:

```markdown
PARALLEL:
- CALL `<проверка A>`;
- CALL `<проверка B>`.

После завершения объединить результаты и провести один GATE общего verdict.
```

Не предлагать `PARALLEL` для зависимых действий или пересекающихся writes.

### Повторное использование capability

Предлагать только когда пользователь или текущий flow явно называет skill и он
присутствует в текущем списке доступных skills:

```markdown
1. CALL SKILL `<skill>`.
2. Передать ему явно названный input.
3. Использовать его результат как вход следующего шага.
```

Не искать skills, не выдумывать их и не предлагать `CALL FLOW` в этой версии.
Одного имени без присутствия в текущем списке доступных skills недостаточно.

Return point: после отчёта и design scan либо после явно выбранной revision;
flow не исполнять.
