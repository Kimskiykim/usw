# Оркестрация с субагентами

Предлагать, когда работа делится на независимые части, а их результаты нужно
свести в один итог. Роль оркестратора исполняет сам flow; субагенты — его
ветки. Развёрнутый рабочий пример — packaged flow `chat-review`.

Контекст-пак каждой ветки — три явных блока:

- Scope: что именно делать и какие точные файлы или данные читать;
- Focus: аспект или критерий этой ветки;
- Output contract: точная форма результата, чтобы сведение было механическим.

Правила:

- передавать ветке минимум необходимого; параллельным веткам не передавать
  результаты друг друга — их независимость и есть ценность;
- зависимость между шагами выражать последовательными `CALL`, передавая
  результат предыдущего шага явно во входе следующего;
- результат ветки возвращается оркестратору в ответе: статус, факты, ссылки,
  blocker. Не заводить state-файл, папку или реестр на субагента —
  координация живёт у оркестратора, durable recovery state есть только у
  root operation;
- durable продукт выполнения (отчёт ревью, сгенерированный документ) пишет
  оркестратор после сводного `GATE`, по явно названному в flow пути; для
  ревью использовать configured `reviews.root`. Ветки держать read-only;
  если ветки обязаны писать — только непересекающиеся явно названные пути;
- потребность в durable state на каждую ветку — сигнал, что ветку пора
  выделить в отдельный flow.

```markdown
PARALLEL:
- CALL SUBAGENT `worker-a`: Scope, Focus, Output contract;
- CALL SUBAGENT `worker-b`: Scope, Focus, Output contract.

1. Свести результаты веток и провести один GATE общего итога.
2. Записать итоговый продукт в `<явный путь>`.
```

#### Конвейер с артефактами по ролям

Предлагать, когда работа проходит стадии, каждая из которых производит
durable деливерабл: например, эксплоратор формирует контекст-пак,
планировщик — план, кодер — evidence, ревьюер — ревью. Стадии зависят друг
от друга, поэтому это последовательная цепочка `CALL`, а не `PARALLEL`;
параллелить можно только реально независимую стадию — например, двух
ревьюеров с двумя отдельными файлами.

Файлы стадий — продукты, не координационный стейт. Границу держат четыре
правила:

- в файле — факты и результат стадии; никаких статусов исполнения, курсоров
  и «продолжить с шага N»;
- один писатель на файл: flow заранее объявляет, какая роль пишет какой файл,
  и никакая роль не дописывает чужой;
- точные пути объявлены в тексте flow до запуска, не пересекаются и лежат под
  понятным root — артефакты изменения под `artifacts.root`, ревью под
  `reviews.root`; субагент получает путь во входе, а не выбирает сам;
- у каждого файла есть контракт формата, чтобы следующая стадия читала его
  механически.

Если при запуске артефакт стадии уже существует, не переиспользовать его
молча: показать находку и вернуть `decision_required` — переиспользовать или
переделать решает человек.

```markdown
1. CALL SUBAGENT `explorer`: собрать контекст по Scope;
   записать `<root>/context-pack.md`.
2. CALL SUBAGENT `planner`: вход — `<root>/context-pack.md`;
   записать `<root>/plan.md`.
3. CALL SUBAGENT `coder`: вход — `<root>/plan.md`;
   записать `<root>/evidence.md`.
4. CALL SUBAGENT `reviewer`: вход — `<root>/evidence.md`;
   записать `<root>/review.md`.
5. GATE ревью:
   - approve → завершить с `completed`;
   - возражения → вернуть `decision_required` с ревью.
```
