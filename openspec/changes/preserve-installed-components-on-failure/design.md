# Design

## Context

Мотивация — `proposal.md`, контракт — delta `component-installation`.
В HEAD `95ab1345582f293e7eb74a76471d4f0e00c27802` source/target списки
заданы в `install.sh`, а `tests/test_install.py` имеет четыре теста с
изолированным HOME subprocess. `check_target` учитывает только `-e`;
preflight исходников отсутствует. `install_skill` удаляет target перед copy,
`install_command` — перед copy файла. Legacy удаляются до установки новых.
Это статическая трассировка причины, не собственный воспроизведённый сбой.

Новая capability отделена от project init. Сохраняются существующие POSIX
shell entrypoint, списки 6 skills / 10 commands, режимы и `--force`.
Текстовая архитектура и ADR-001 не затрагиваются. Требования к состоянию
задачи и evidence берутся из `execution-artifacts`, а не из нового runtime.

## Goals / Non-Goals

**Goals:** полная подготовка до разрушительного шага; управляемые отрицательные
тесты, показывающие прежние bytes и понятный ненулевой результат.

**Non-Goals:** см. proposal. Отказ диска во время восстановления может оставить
backup вместо активного target; сохранить backup и сообщить путь обязательно.
Не вводить журнал транзакций, daemon, machine DSL или новый Python installer.

## Decisions

### 1. Preflight всего выбранного набора

До `install_agent` проверить все шесть source directories с `SKILL.md`,
все десять source command files и targets выбранных агентов, включая legacy.
Для занятости конечной записи использовать `-e` либо `-L`. Без force любой
конфликт завершает работу до mutation. С force leaf symlink заменяется как
запись, а не разыменовывается. Source/target roots текущей установки различны;
совпадение roots остаётся AUD-S11 и не получает здесь no-change вердикта.
Symlink рассматривается только в конечном target; обработка родительских
ссылок вне change. Отдельные workspace write-safety правила из context не меняются.

Альтернатива — проверять исходник только перед каждым copy: поздняя потеря
исходника всё ещё допускает ненужное изменение ранних компонентов и legacy.

### 2. Подготовленная копия рядом с назначением

Использовать уникальный временный каталог под тем же parent назначения.
Skill копировать внутрь с прежней структурой; удалять bytecode/cache в копии.
Command также сначала копировать во временный объект. Ошибка copy или очистки
копии завершает попытку до изменения target. Проверить команды явно, чтобы
`set -e` и cleanup не маскировали первичную ошибку.

Альтернатива — copy поверх старого target: смешивает деревья и усекает файлы.
Готовить весь пакет сразу не нужно: это другая стоимость и другая гарантия.

### 3. Переключение с сохранением прежнего объекта

При занятом target переместить саму запись в уникальный backup внутри
временного каталога; переместить подготовленную запись на точный target,
не внутрь старого directory. Если второе перемещение не удалось, вернуть
backup. Удалять backup только после успешной активации. Cleanup удаляет
только собственные незавершённые staging objects; backup при неудачном
rollback сохраняется и называется в ошибке. Для отсутствовавшего target
неудачная подготовка не создаёт неполный компонент по его имени.
При отказе финального cleanup после активации вернуть ненулевой exit,
сохранить новый полный target и назвать точный оставшийся путь. Не откатывать
успешную активацию ради cleanup; сообщение успеха компонента отложить до очистки.

Command можно переключать обычным rename; единый небольшой helper допустим,
если он упрощает одинаковые ветки skill и command. Выбор shell functions
остаётся исполнителю. Нет общей rollback-цепочки уже обновлённых компонентов.
Сообщение ошибки раскрывает возможную смешанную редакцию и запрет считать
весь пакет обновлённым до проверки.

### 4. Доказательство через fault injection в subprocess

Расширить существующий unittest-файл. Изменяемые исходные fixtures копировать
в temporary source checkout; никогда не удалять source текущего проекта.
Для отказов copy, удаления bytecode, rename и cleanup использовать временный
PATH с wrapper, который исполняет заданную последовательность отказов,
остальные операции делегирует реальной команде. Для rollback failure отдельно
отказать активации, затем восстановлению; сообщённый путь сопоставить с полным
сохранённым backup. Для partial copy skill и command сначала создать часть копии,
затем возвращает ошибку. Это проверяет обработку результата команды, а не
реальное переполнение диска. Сравнивать рекурсивные bytes, тип target и
link-target; для skill включить вложенные файлы и sentinel только старой версии,
для command — точные bytes. Проверять имя компонента в ошибке, ненулевой exit,
отсутствие ложного success и cleanup staging/backup после успеха и отказа.

Минимальная матрица: missing late source; поздний конфликт режима all;
partial skill copy; partial command copy failure; новый target при copy failure;
bytecode cleanup failure до активации; final cleanup failure после активации;
activation rename failure с успешным rollback; rollback failure с сохранённым
backup; regular и dangling leaf symlink без force/с force; поздняя ошибка
после раннего успеха. Успех и legacy removal защищают прежние четыре теста.
Не привязывать assertions к целому предложению диагностики.

## Risks / Trade-offs

- Смешанная редакция при поздней ошибке → явная диагностика, сверка пакета,
  повтор отдельным назначенным шагом; global transaction не обещается.
- Дополнительные временные bytes → staging одного компонента, cleanup по
  завершении; backup после rollback failure намеренно остаётся.
- POSIX rename/`cp` различаются между хостами → реальные утилиты macOS в
  локальных тестах; Linux проверяется имеющимся CI при его доступности.
- Ошибка installer затрагивает доступность всех skills → обновлять общую
  установку только после отрицательных и положительных fixture-тестов.

## Migration Plan

1. Новый рабочий разработчик получает apply отдельным поручением; рекомендуемый
   маршрут — `.usw/state/autonomous-improvement/2026-11-10/planning-initial.md`.
   Этот operational flow не входит в product diff S10 и не заменяет OpenSpec apply.
2. Сначала воспроизвести дефект тестом, затем править installer и документацию.
   После последней правки выполнить локальные checks; critics читают именно
   этот diff и evidence. До реальной установки все вызовы USW завершить с
   Outcome/readback, сохранить текущую редакцию и сценарий продолжения.
3. Единственный писатель выполняет `./install.sh codex --force`, сохраняет
   command/exit/output. При ошибке не возвращать вызовы USW до сверки/восстановления.
4. Новый тестировщик после установки сверяет состав/bytes 73+10 и выполняет
   обычную полезную задачу через USW, затем Save/продолжение в новой сессии.
   Старые рабочие чаты USW больше не вызывают. Критик проверяет эту редакцию.
5. Verify → sync/archive по применимым skills; никакой автоматической очистки
   других changes. Аналитик дополняет историю только AUD-S10 фактами и
   границами, затем актуализирует его строку индекса. Постоянный контекст
   не меняется без нового обобщённого факта; правило installer живёт в spec,
   README ссылается. Коммитер фиксирует принятый ограниченный diff.
