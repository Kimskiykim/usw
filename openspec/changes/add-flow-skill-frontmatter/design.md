## Context

Мотивация и границы — в `proposal.md`. Основа: `03-architecture.md` и
`ADR/ADR-001-text-first-execution.md`. `run_flow.py` уже возвращает полный
Markdown и хеширует исходные байты; `write` принимает весь документ через stdin.
В `find-flow` есть предварительный отбор по имени, который сейчас мешает
обнаружению по описанию. Установленные скиллы не читают изменения checkout
автоматически, поэтому обновление установки — отдельный завершающий шаг.

## Goals / Non-Goals

**Goals:** один формат описания пакета инструкций; совместимость flat/package
и старых файлов; использование описания в discovery; проверяемая граница
между метаданными и исполнением.

**Non-Goals:** повторять scope из proposal не требуется. Дополнительно:
не обещать экономию контекста через загрузку только заголовков — существующий
безопасный загрузчик возвращает весь документ.

## Decisions

### 1. Общая форма заголовка, отдельный способ загрузки

Ориентир — [Agent Skills specification](https://agentskills.io/specification),
проверена 2026-09-22. Обязательные поля и их ограничения зафиксированы в
`flow-frontmatter`. Используется существующий ASCII kebab-case USW; для flat
совпадение имени проверяется с основой файла, для package — с каталогом.
Ограничение 64 символа относится к новому authoring, не ломает старые selectors.

```markdown
---
name: review-changes
description: Проверять изменения перед коммитом. Использовать для ревью diff.
compatibility: Требуется Git.
metadata:
  author: usw
  version: "1.0"
  category: review
---

# Проверка изменений

1. Прочитать diff.
2. Проверить изменённое поведение.
3. Вернуть замечания.
```

В примере показаны известные для него дополнительные сведения. В общем случае
`compatibility` и `metadata` необязательны: create-flow добавляет только
обоснованные или запрошенные данные и показывает их вместе с черновиком.
Ограничения типов и длины определены в `flow-frontmatter`; `metadata.tags`,
если нужен, записывается строкой, например `"review, git"`. Автор и версия
не назначаются автоматически. `metadata.version` описывает версию пакета,
не выбирает `version-2` и не вызывает миграцию.

`compatibility` помогает человеку и модели увидеть требования, но не заменяет
действующие проверки зависимостей. Discovery по-прежнему сопоставляет имя и
описание; индексирование, фильтры по тегам и версиям не добавляются.
Остальные стандартные поля и расширения сохраняются при правках; USW не
реализует клиентские флаги активации и не считает `allowed-tools` разрешением.
Спецификация формата навыков служит источником формы, а семантика USW
закреплена собственной дельтой.

### 2. Первый этап без машинного разбора YAML

Выбран вариант «заголовок + правила скиллов». Полноценный YAML-парсер добавил бы
зависимость, требования к установке и новый API ошибок. Самописный ограниченный
парсер создавал бы несовместимый диалект. Оба варианта отложены; гарантии
правильности метаданных моделью не заявляются. При необходимости детерминизма
нужен отдельный change с явным разрешением зависимости и поддерживаемой схемой.

`resolve`, `inspect`, `resource`, `prepare-write`, `write` сохраняют сигнатуры и
JSON. Ни `metadata`, ни отдельный `body` в JSON не добавляются. Проверки на
сырой Markdown, identity, stale token и неизменность файлов остаются точными.

### 3. Роли четырёх скиллов

- `create-flow`: показывает заголовок в первом черновике нового flow; при
  наличии данных добавляет `compatibility` и `metadata`; при редактуре
  сохраняет метаданные и границу разрешения конкретного diff.
- `find-flow`: перечисляет допустимые прямые entrypoints, безопасно читает
  кандидатов и сопоставляет описания; имя не служит исключающим фильтром.
- `assess-flow`: различает дефект метаданных и дефект процесса. Ошибка
  заголовка сообщается отдельно и сама по себе не меняет вердикт; отсутствие
  заголовка у старого flow допустимо.
- `run-flow`: получает полный Markdown и использует тело как процесс;
  идентичность, пути и полномочия остаются внешними по отношению к заголовку.

Общий контракт имеет один дом `flow-frontmatter`; в скиллах остаются только
необходимые исполнимые инструкции и ссылки на контракт.

### 4. Совместимость и поставляемые файлы

Пользовательские flow не мигрируют при init/run/find/assess. Правка тела старого
flow не добавляет frontmatter автоматически. Если пользователь просит новый
файл строго без заголовка, create-flow сначала согласует противоречие.

Заголовки добавляются к восьми tracked entrypoints в `usw/flows/` и четырём
примерам в каждом из `usw/flows/examples/` и
`skills/usw-initialize-project/templates/flows/examples/`. README каталогов,
рецепты, исследовательские файлы и `.usw/flows/` не мигрируют. Тела сохраняются
побайтно. Init остаётся аддитивным: уже созданные примеры не переписываются.

## Risks / Trade-offs

- Модель может ошибиться в YAML → обычные и многострочные описания, сохранение
  дополнительных полей и ошибки заголовка включены в eval; не выдавать это за
  машинную валидацию.
- Discovery читает больше entrypoints → честно зафиксировать линейное чтение
  прямых кандидатов; индекс/metadata-only CLI не добавлять в этот change.
- Старые authoring eval требуют точного файла без заголовка → новые создания
  получают ожидаемый frontmatter; проверки тела и отсутствия скрытых правок
  сохраняются. Старые edit fixtures остаются без заголовка для совместимости.
- `equals_flow` нормализует CRLF → точные гарантии проверять отдельным
  сравнением байтов в regression/smoke; харнесс в этом change не расширять.
- Текст метаданных может противоречить телу → не переадресовывать вызов;
  обнаруженную неоднозначность действия обрабатывать обычным правилом.

## Migration Plan

Три зелёных коммита: A — этот план и дельты; B — скиллы, tests/evals и
синхронизация основных спецификаций; C — заголовки поставляемых flow и примеров,
README, проверки неизменности тел. Каждый коммит проверяется через stash-verify.
После полного прогона — verify/archive change. Установленные копии обновлять
отдельным явно запрошенным действием. Откат к прежним инструкциям не требует
удаления заголовков: старый resolver уже читает их как часть Markdown.
