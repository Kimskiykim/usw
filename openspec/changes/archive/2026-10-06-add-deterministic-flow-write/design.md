## Context

Runtime resolver уже безопасно выбирает flat или packaged entrypoint через
общий `safe_access.py`, но CLI принимает вычисленный вызывающим shared root и
предоставляет только read-пути `resolve`, `inspect` и `resource`.
`usw-create-flow` независимо повторяет выбор root, раскладки и проверки перед
записью в текстовых инструкциях. Нужно перенести этот протокол в существующий
resolver, сохранив его текущие read-контракты и обе платформенные реализации.

Change опирается на уже реализованную раскладку из `support-packaged-flows`, но
не синхронизирует тот change с main-спекой.

## Goals / Non-Goals

**Goals:**

- Детерминированно вычислять authoring root из точной открытой папки проекта и
  её `usw.yaml`.
- Возвращать модели один подготовленный entrypoint и его текущий Markdown.
- Связывать подготовку и запись токеном состояния и повторно проверять оба
  кандидата непосредственно перед атомарной записью.
- Использовать существующие config parser и safe-access boundary на POSIX и
  Windows.
- Не читать и не изменять соседние package resources.

**Non-Goals:**

- Новый `create_flow.py`, Markdown parser, DSL validator или resource editor.
- Изменение `resolve`, `inspect`, `resource`, design scan либо
  `guided-flow-authoring`.
- Синхронизация `support-packaged-flows`.
- Межпроцессный lock или транзакция файловой системы против процесса, который
  намеренно меняет путь в наносекундном окне самого atomic replace.

## Decisions

### Добавить `prepare-write` и `write` в существующий CLI

`prepare-write <project> <name> [--origin local|shared]` вычисляет root,
проверяет обе раскладки и возвращает JSON: `name`, `origin`, `layout`, точные
`path` и `flow_directory`, признак существования, текущий `markdown`, identity
и `write_token`. Без selector origin равен `shared`, как в действующем
authoring-контракте.

`write <project> <name> <write_token> [--origin ...]` принимает новый Markdown
через stdin, повторяет подготовку, сравнивает token, снова проверяет кандидаты
в открытом безопасном parent directory, атомарно заменяет только выбранный
entrypoint и возвращает результат read-back. Разделение сохраняет человеко-
управляемый цикл черновика и согласования между чтением и записью; одна команда
сразу с content не позволила бы безопасно редактировать существующий текст.

### Загружать config parser из initialize-project

`run_flow.py` загружает `init_usw.py` тем же sibling-module механизмом, которым
уже загружает `safe_access.py`, и вызывает `load_config` для точного
`<project>/usw.yaml`. Shared root равен `<project>/<config.flow_root>`, local
root остаётся `<project>/.usw/flows`. Ошибки `ConfigError` преобразуются в
обычный JSON error с тем же стабильным code. Дублирование YAML subset parser
отклонено как второй источник истины.

### Токен связывает все решения, влияющие на цель

`write_token` — SHA-256 от versioned JSON, содержащего origin, абсолютный root,
имя, layout, целевой путь, состояние существования root, package и entrypoint
и identity существующего Markdown.
Изменение config/root, появление второй раскладки, смена layout или содержимого
entrypoint приводит к `stale_flow_target`. Token не является полномочием или
секретом; он только обнаруживает изменение состояния между командами.

### Писать через safe directory и same-directory replace

Для нового package безопасный flow root создаёт прямой каталог `<name>` либо
открывает уже существующий безопасный каталог, после чего эксклюзивно создаёт
`FLOW.md`. Для существующего entrypoint writer создаёт случайный временный
regular file в том же directory, fsync-ит его, ещё раз проверяет layout и
identity и заменяет entrypoint через `SafeDirectory.replace`. Временный файл
удаляется при отказе. Затем resolver перечитывает entrypoint через тот же
boundary и подтверждает точные записанные символы.

Соседние имена package не перечисляются и их bytes не открываются. Добавление
отдельного общего writer abstraction отклонено: текущей операции достаточно
малой поверхности `SafeDirectory`.

### Сохранить существующие error-контракты

Используются действующие `invalid_flow_name`, `invalid_flow_origin`,
`ambiguous_flow_layout`, config- и safe-access codes. Несовпадение подготовки
возвращает новый `stale_flow_target`; невалидный stdin UTF-8 возвращает
`invalid_flow_encoding`. Ошибки остаются JSON в stderr с exit code 2 для
любого входа: искажённый или не-ASCII token сравнивается обычным строковым
сравнением (token — не секрет, `secrets.compare_digest` заменяется) и даёт
`stale_flow_target`, а не traceback. Добавляются коды
`workspace_not_initialized`, `empty_flow_content` и `write_unverified`.

### Создавать отсутствующий root при write

`prepare-write` остаётся read-only: при отсутствующем root он возвращает цель
внутри него, включая состояние существования root, package и entrypoint в
`write_token`. Недостающие компоненты создаёт только `write`, тем же
механизмом, что package-каталог: покомпонентно, только внутри `<project>`, с
проверкой containment/symlink/типа на каждом шаге. Разделение случаев:
shared root создаётся целиком; local `.usw/flows` создаётся только внутри уже
существующей `.usw`; отсутствующая `.usw` останавливает ещё prepare с
`workspace_not_initialized` — молча создавать workspace без `.gitignore`
нельзя, это зона `usw-init`, и SKILL предлагает пользователю инициализацию.

### Отклонять пустое содержимое

Пустой или состоящий из одних пробельных символов Markdown отклоняется с
`empty_flow_content` до каких-либо изменений — по прецеденту
`prepare_markdown_run`, который уже отклоняет пустой input. Легитимного
сценария «записать пустой flow» нет; это закрывает молчаливое затирание
существующего flow сломанным redirect или упавшим producer.

### Выравнить разбор `flows.root` в общем parser

Root-cause фикс в `init_usw.py`, а не обходной в runner: mini-YAML parser
срезает inline-комментарии, а потребители конфига строят путь из уже
нормализованных `_root_parts` (разделители приведены к `/`), а не из сырой
строки. Так одинаково чинятся init и authoring. Полный перевод модельного
чтения `usw.yaml` в run/find/assess на этот же parser — вне scope, отдельный
change.

### Различать ошибки до и после состоявшейся замены

Все отказы до `replace` сохраняют контракт «ничего не записано». Ошибка после
состоявшейся замены — сбой `sync` каталога, несовпадение/сбой read-back или
прерывание через Ctrl+C при перечитывании —
возвращает отдельный `write_unverified` с явным указанием, что entrypoint уже
заменён. SKILL сообщает «записано, но проверка не подтверждена», а не
«остановился без записи».

### Убирать созданные каталоги при отказе

`make_directory` для package выполняется после `_assert_write_target`,
непосредственно перед staging. При любом обработанном отказе после создания
каталогов текущая попытка удаляет созданные ею пустые каталоги новым
примитивом `SafeDirectory.remove_directory` — не-рекурсивный `rmdir`
(descriptor-бэкенд — через `dir_fd`), `ENOTEMPTY` от каталога, успевшего
получить чужие записи, молча допускается. Очистка повторно проверяет безопасный
путь родителя; при его внешней подмене она не следует перенаправлению.
Сбой удаления не заменяет исходную ошибку записи: её код сохраняется,
а описание ошибки `FlowError` дополняется причиной неудачной очистки.
При такой ошибке созданные каталоги могут остаться.
Успешная очистка возвращает ФС в
состояние prepare, поэтому `write_token` остаётся валидным для повторной
попытки. Crash-окно между созданием и очисткой остаётся задокументированным
остатком.

### Сохранять обычные права файлов

Замена существующего entrypoint сохраняет его текущий режим. Новые entrypoint
и каталоги создаются с обычными правами по умолчанию (0o644/0o755 с учётом
umask), а не owner-only: shared flow — обычный коммитимый файл проекта.
Режим 0o600 остаётся политикой только handoff-артефактов.

## Risks / Trade-offs

- [Pathname backend на Windows не закрывает check/use окно полностью] →
  повторять проверку в самом writer и сохранять описанное платформенное
  ограничение; не ослаблять проверки link/reparse-point.
- [Crash строго между созданием каталогов и их очисткой] → пустой каталог
  может остаться при аварийном завершении процесса; при неизменных безопасных
  путях обработанные ошибки убирают его, частичный Markdown не публикуется, повторный запуск
  безопасно использует оставшийся directory.
- [Изменение config между prepare и write] → включить resolved root, origin и
  состояние существования root/package/entrypoint в token и повторно
  загрузить config.
- [Модель может вызвать `write` с другим selector] → token связывает origin и
  path, поэтому команда отказывает без записи.
- [Гонка в окне между rename и read-back] → отказ помечается как
  `write_unverified` с фактом состоявшейся замены; контракт «ничего не
  записано» кодов stale/unsafe не нарушается.
- [Родительский путь подменён внешним процессом во время staging] → повторная
  проверка останавливает запись до замены. Очистка не следует подменённому
  пути: временный файл в перемещённом исходном каталоге может остаться,
  но чужие файлы и каталоги не удаляются.

## Migration Plan

После установки обновлённый create-flow использует новые субкоманды. Existing
flat/package flows не перемещаются. Rollback возвращает прежний SKILL.md и
runner; созданные package flows остаются совместимыми с реализованной package
раскладкой.
