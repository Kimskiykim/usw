# Design

## Context

Мотивация и границы — в [proposal.md](proposal.md). `usw-create-flow` уже читает `references/recipes.md`, выбирает применимые блоки и после записи делает один ограниченный scan. В каталоге 15 рецептов; `subagent-orchestration.md` смешивает независимые ветки и фиксированный конвейер с файлами. Общего словаря именованных паттернов нет.

`tests/test_package_layout.py` фиксирует набор рецептов и файлов верхнего уровня references; `tests/test_flow_scenarios.py` также проверяет этот уровень. Сценарии `create-goal-blocks`, `create-design-scan` и `create-design-scan-rejected-recipe` уже проверяют границы согласования. Это точки расширения, а не новый механизм выполнения.

Дизайн нужен для согласования нескольких текстовых слоёв и устранения неоднозначности классификации. Он следует `03-architecture.md` и `ADR-001-text-first-execution.md`.

## Goals / Non-Goals

**Goals:** дать автору flow короткий словарь для обсуждения структуры; хранить каждое правило в одном месте; загружать подробности только для выбранных рецептов.

**Non-Goals:** техническая регистрация паттернов, новые опции CLI, автоматическая оркестрация, обязательная схема отчётов, переделка установщика и существующих flow. Границы из proposal сохраняются.

## Decisions

### 1. Термины и два уровня справочника

Определения «паттерн / рецепт / flow» живут в `openspec/context/02-domain-glossary.md`. Нормативный контракт каталога — `flow-design-patterns`, поведения автора — `guided-flow-authoring`. Устанавливаемые инструкции остаются самодостаточными и ссылаются на имена контрактов; отсутствие OpenSpec в пользовательском проекте не должно препятствовать созданию flow.

`references/recipes.md` остаётся единственным кратким индексом выбора. В его записях рядом с условиями находятся исходные имена связанных паттернов и ссылки на карточки. Тот же индекс содержит короткие строки для подходов с зависимостями среды, даже если готового рецепта нет; такие строки не маскируются под доступные capabilities. Подробные карточки располагаются в `references/patterns/<slug>.md`; рецепты — в существующем `references/recipes/`. Отдельный индекс паттернов, YAML registry и поиск по сети во время обычного создания flow не нужны.

Альтернатива — один большой справочник в SKILL.md — отклонена: он увеличивает каждый контекст и дублирует рецепты. Карточки загружаются вместе с выбранными рецептами либо по явно названному подходу без готового рецепта; базовый пример в карточке — обычная проза, поэтому чтение не переключает автора в `version-2`.

### 2. Состав и соответствие рецептам

| --- | --- | --- |
| `pipeline.md` | Sequential workflow / Pipeline; Prompt chaining — частный случай | новый `sequential-stages.md` |
| `routing.md` | Router / Dispatcher / Routing | новый `routing.md`; escalation/adaptive-intensity — специализированные варианты |
| `sectioning.md` | Parallelization: Sectioning | новый `independent-work.md`; `independent-checks.md` — read-only вариант |
| `voting.md` | Parallelization: Voting | новый `independent-voting.md`; связь с `subagent-review.md` |
| `orchestrator-workers.md` | Supervisor / Orchestrator–workers | `subagent-orchestration.md`: динамический выбор подзадач |

| `claim-check.md` | Claim Check | новый `artifact-passing.md` |
| `fan-out-fan-in.md` | Fan-out / Fan-in | общая схема разветвления/сведения; композиции Sectioning или Voting, без второго рецепта параллельности |
| `hierarchical-decomposition.md` | Hierarchical decomposition | ограниченная композиция `subagent-orchestration.md`; явная глубина и возврат результатов, только при поддержке host |
| `handoff.md` | Handoff — передача управления | условный подход: требуется реальная передача активного управления; не команда recovery-handoff USW |
| `group-discussion.md` | Group chat / Debate / Council | композиция `subagent-orchestration.md` и `human-decision.md`: обмен позициями в ограниченных раундах |
| `planner-executor-replanner.md` | Planner–executor–replanner; Magentic — связанный пример | композиция планирования, выполнения и bounded-refinement; пересмотр оставшегося плана по evidence |
| `blackboard.md` | Blackboard | условный подход: общие знания, явные writers, выбор следующей работы и обработка конфликтов; общий каталог файлов сам по себе недостаточен |
| `shared-work-queue.md` | Общая очередь задач / Shared work queue | условный подход: host предоставляет эксклюзивный захват и восстановление; без этого — последовательное назначение |
| `context-isolation.md` | Изоляция контекста субагентов | механизм в `subagent-orchestration.md`, сочетаемый с `artifact-passing.md`; учитывает реальные правила наследования контекста |

Новые рецепты нужны там, где существующий блок не охватывает обещанный выбор. Например, «Независимые проверки» ограничены read-only проверками, а «Ревью субагентами» допускает одного reviewer и не является полным рецептом нескольких оценок. Старые имена и пути сохраняются. В `subagent-orchestration.md` подробности передачи файлов переносятся в `artifact-passing.md`, на месте остаётся ссылка; фиксированный конвейер больше не выдаётся за динамическую декомпозицию.

Структура карточки соответствует новой спецификации. Прикладные фрагменты живут в рецептах; карточка содержит только короткий поясняющий пример и ссылку, без второй копии исполняемых инструкций. Для Pipeline достаточно нескольких последовательных шагов, без обязательных агентов.

Для иерархии, обсуждения, перепланирования и изоляции достаточно коротких разделов в существующих рецептах оркестрации и ограниченной доработки. Они задают глубину делегирования, предел раундов, входы, возврат результатов и условия смены плана. Maker–checker использует существующее ревью без автоматического исправления. Отдельный файл рецепта для каждой карточки не требуется.

Карточки Handoff, Blackboard и очереди не исключаются из индекса из-за зависимостей. Они объясняют условие применения и альтернативу при его невыполнении. Этот change не добавляет передачу root ownership, базу Blackboard, event scheduler, lock-файлы или очередь. Изоляция контекста — свойство доступного host-вызова и выбранных входов; передача всей истории по запросу пользователя допустима, но не описывается как чистый контекст.

### 3. Источники и граница аналогий

Карточки с подходами Anthropic ссылаются на [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents); Claim Check — на [Enterprise Integration Patterns](https://www.enterpriseintegrationpatterns.com/patterns/messaging/StoreInLibrary.html). В первой статье речь о программно организованных workflows; перенос в модельно исполняемый Markdown явно помечается адаптацией. Pipeline шире Prompt chaining; Fan-out / Fan-in описывает форму ветвления и сборки.

Приложенный текст служит источником намерения и обсуждения композиции, но не объявляет новый отраслевой стандарт. Сочетание оркестратора, файлов и ревью помечается композицией USW. Подробности источников перефразируются кратко; статьи целиком в поставку не копируются.

### 3.1. Сверка покрытия исходных материалов

Граница сверки — весь первый приложенный текст и дополнение Building effective agents; ссылки из текста используются для проверки смыслов. Позиции не исключаются как «контекст» только потому, что им нужна отдельная поддержка. Синонимы сохраняются для поиска, но различия формулируются по поведению.

Источники: A — [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents); B — [Claim Check](https://www.enterpriseintegrationpatterns.com/patterns/messaging/StoreInLibrary.html); C — [ADK workflow patterns](https://adk.dev/workflows/patterns/); D — [Microsoft orchestration](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/ai-agent-design-patterns); E — [LangChain subagents](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents); F — [Blackboard](https://www.cs.cmu.edu/~ModProb/MRsol4.html); G — [Building a C compiler](https://www.anthropic.com/engineering/building-c-compiler). «Вложение» обозначает пользовательский исходник; это не ссылка на отраслевой стандарт.

### 4. Интеграция в создание flow

Автор читает индекс, выбирает блоки по задаче, называет соответствующий паттерн с одной причиной, затем показывает обычные шаги. Он не проводит отдельный обязательный опрос по каждому названию и не превращает список паттернов в пользовательскую конфигурацию.

На стадии согласования сохраняется существующее правило чтения файлов одобренных блоков. При scan читаются выбранные рецепты и их карточки, всего не более трёх подробных предложений по рецептам. Несколько паттернов у одного рецепта не увеличивают лимит. Отклонённая функциональность не возвращается под другим именем; готовый текст не переписывается ради терминологии.

Альтернатива — требовать перечень паттернов в каждом FLOW.md — отклонена: пользователю нужны понятные действия, а метаданные и runtime менять не требуется. README получает только краткую навигацию; подробности остаются в справочнике.

### 5. Применение первоначальной идеи без нового runtime

Рецепт передачи файлов сохраняет один объявленный writer на артефакт и требования напрямую для каждого релевантного исполнителя. Его короткий ответ сообщает факт завершения, ссылку и актуальную версию результата; при проверке отдельно указываются вердикт и непроверенные критерии. Это требования к содержанию guidance, не обязательная YAML-схема и не новый persistent state.

Ревью читает фактический результат и исходные требования, а не только evidence автора. Способ привязки к версии берётся из применимого контракта: для существующих v1 задач — `execution-artifacts`, без навязывания этой модели любому flow. Handoff остаётся необязательным recovery state корня. Отдельная реализация протокола восстановления частичных файлов и версий отложена согласно обсуждению.

Voting требует выбранного правила сведения и видимых разногласий, не подменяет evidence количеством голосов. Это не меняет действующий `chat-review` и его human gate. В `bounded-refinement.md` достаточно добавить пример отсутствия прогресса в пределах уже заданного лимита; запускать исправления без предусмотренного flow разрешения нельзя.

Автономность объясняется короткой заметкой в карточке Orchestrator–workers как отдельная степень свободы выбора шагов. Она не создаёт дополнительный обязательный паттерн или рецепт автономного агента. Augmented LLM, retrieval, инструменты и память поясняются в той же карточке как базовые компоненты, не как формы оркестрации. Scope, пределы и момент обращения к человеку должны быть явными, когда такая свобода запрошена.

### 6. Проверка результата

Детерминированно проверить полный набор карточек, обязательные поля, локальные ссылки и соответствие рецептам; обновить точные наборы в существующих layout-тестах. Наличие терминов не доказывает правильный выбор моделью.

Сначала сверить каждую строку §3.1 с каталогом: 16 карточек и два поясняющих раздела о композиции и базовых компонентах. Подход без готового рецепта считается покрытым только с указанными зависимостями и понятным ограничением. Ни совпадение числа файлов, ни прежний вердикт ревью не заменяют эту сверку.

Behavior evals проверяют простой линейный запрос, динамическую декомпозицию, Sectioning против Voting, запрет параллельных пересекающихся записей, композицию с Claim Check и запрет повторного предложения отклонённого рецепта под alias. Дополнительно проверяются Handoff против recovery, Group chat против Voting, Maker–checker без цикла, ограниченная иерархия/перепланирование, явные зависимости Blackboard/очереди и честное описание изоляции при унаследованной истории. Существующие create-сценарии проверяют отсутствие регрессий согласования, scan и стилей. После правки SKILL.md выполняется предусмотренный проектом прогон evals; результаты — наблюдения, а не обещание безошибочного исполнения.

Существующий runner автоматически проверяет status, markers и файлы, но не смысл ответа. Поэтому каждый новый сценарий разделяет автоматические assertions и критерии ручного чтения сохранённого транскрипта: выбранный подход соответствует зависимостям задачи; шаги реализуют заявленный паттерн; отклонённый блок не возвращается перефразированным; неполные проверки не объявлены успехом. Для каждого применимого критерия фиксируются `pass`, `fail` или `unchecked` и фрагмент evidence со ссылкой на транскрипт. Зелёные маркеры без такого разбора не доказывают семантическое требование. Это использует действующий подход `create-design-scan-rejected-recipe`, без нового evaluator или изменения runner.

## Risks / Trade-offs

- Разрастание справочника → 16 коротких карточек, один индекс, reuse рецептов и выборочное чтение; полнота названий не требует 16 новых механизмов.
- Авторитетные названия создают иллюзию гарантий → атрибуция адаптации и явная ссылка на text-first границу.
- Один блок предлагается повторно под alias → сопоставление по смыслу рецепта и отдельный отрицательный eval.
- Смешение статуса и вердикта → пример Claim Check показывает оба понятия, не создавая новую схему состояния.
- Затраты на агентов и артефакты → карточка объясняет условия неприменимости и проверку пользы; простой путь остаётся исходным.

## Migration Plan

Изменение аддитивно для пользователей: обновляются исходники skill и справочники, существующие flow не мигрируют. Сгенерированные пользовательские копии обновляются штатной установкой; текущая работа их не правит. Откат возвращает прежние исходники guidance и связанных тестов, не затрагивая созданные пользователями flow или handoff.
