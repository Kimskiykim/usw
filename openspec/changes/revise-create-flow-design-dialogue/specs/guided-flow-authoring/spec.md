## MODIFIED Requirements

### Requirement: Успешное создание включает bounded design scan
После первоначальной записи и отчёта о запрошенном flow `usw-create-flow` SHALL
автоматически выполнить один read-only design scan. Scan SHALL сначала прочитать
каталог рецептов `references/recipes.md` и по указанным в каталоге условиям
выбрать не более трёх наиболее релевантных рецептов, отдавая приоритет пробелам
в безопасности и проверяемости результата. Skill SHALL прочитать только файлы
выбранных рецептов под `references/recipes/`; другие применимые рецепты SHALL
быть названы одной строкой по каталогу без чтения их файлов. После первой
разрешённой revision design scan MUST NOT запускаться повторно и новые рецепты
MUST NOT предлагаться автоматически; обсуждение уже предложенных правок MAY
продолжаться.

#### Scenario: У flow несколько design-пробелов
- **WHEN** сохранённый flow можно улучшить более чем тремя рецептами
- **THEN** skill возвращает три наиболее релевантные подсказки без изменения
  файла и читает только файлы этих трёх рецептов

#### Scenario: У flow нет конкретного design-пробела
- **WHEN** ни один рецепт не устраняет конкретный риск или отсутствующий outcome
- **THEN** skill сообщает, что полезных подсказок нет, и завершает работу

#### Scenario: Применимых рецептов больше лимита подробного scan
- **WHEN** помимо выбранных трёх остаются другие применимые рецепты
- **THEN** skill называет каждый из них одной строкой, без подробностей и без
  чтения их файлов

#### Scenario: Revision применена
- **WHEN** пользователь разрешил запись одной подсказки и revision записана
- **THEN** skill не запускает новый design scan и не предлагает новые рецепты
  автоматически, но может продолжить обсуждение ранее предложенных правок

#### Scenario: Пользователь заранее пропускает запись подсказок
- **WHEN** пользователь просит показать design scan, заранее отказавшись от
  записи его предложений
- **THEN** skill показывает применимые подсказки без записи; этот отказ не
  считается отклонением рецептов при согласовании структуры

### Requirement: Каждая подсказка применима
Каждая подсказка MUST указывать, что добавить, объяснять пользу именно для
сохранённого flow и показывать готовую правку в блоке unified diff с путём
entrypoint и контекстом сохранённого файла. Контекст и удаляемые строки MUST
однозначно определять место правки; точность номеров строк hunk не является
критерием применимости. Рецепты, отклонённые при согласовании структуры текущего
flow, MUST NOT предлагаться в design scan, включая краткий список остальных
применимых рецептов. Когда fragment преобразуется в обычную прозу из рецепта,
пример которого содержит contract tokens в обратных кавычках — статусы и
варианты решения, которые человек вводит в ответ, — эти tokens SHALL
сохраняться дословно, а не переводиться.

#### Scenario: Обычный flow получает guidance
- **WHEN** сохранённый flow использует обычный Markdown
- **THEN** предлагаемый fragment использует обычную прозу без structured markers

#### Scenario: Structured flow получает guidance
- **WHEN** сохранённый flow использует structured authoring
- **THEN** предлагаемый fragment MAY использовать только применимые markers
  `CALL`, `GATE`, `LOOP` и `PARALLEL`

#### Scenario: Contract tokens рецепта сохраняются при преобразовании в прозу
- **WHEN** contract tokens из примера рецепта, например `approve`, `change` и
  `cancel`, встраиваются в обычный flow
- **THEN** tokens сохраняются дословно, а окружающие markers превращаются в
  обычную прозу

#### Scenario: Дифф показывает место вставки
- **WHEN** предлагается добавить шаг в сохранённый flow
- **THEN** дифф называет entrypoint и содержит достаточный контекст для
  однозначной вставки; смещение номера строки само по себе не отклоняет правку

#### Scenario: Рецепт отклонён при проектировании от цели
- **WHEN** рецепт применим по каталогу, но пользователь отклонил его при
  согласовании структуры текущего flow
- **THEN** после сохранения рецепт отсутствует среди подробных и кратких
  рекомендаций design scan

### Requirement: Revision остаётся под контролем человека
`usw-create-flow` MUST изменять сохранённый flow только по явному указанию
пользователя записать конкретную, однозначно определённую правку. Указание MAY
быть выражено свободным текстом или номером варианта, который явно предлагает
эту запись; обязательного токена нет. Выбор темы обсуждения, просьба
переработать предложение и неоднозначное согласие MUST NOT разрешать запись.
Без разрешения сохранённый flow MUST оставаться byte-for-byte неизменным.
Skill MUST сохранять выбранные origin, authoring style и flat или packaged
layout entrypoint.

Число пользовательских итераций доработки SHALL быть неограниченным, а ожидание
ответа SHALL возвращать управление пользователю. Каждая запись MUST иметь
собственное явное разрешение, предварительное чтение актуального файла,
повторную проверку безопасности непосредственно перед записью и перечитывание
результата. Если актуальный файл изменился так, что меняется согласованная
правка, skill MUST показать обновлённый дифф и получить новое разрешение.

#### Scenario: Пользователь выбирает одну подсказку
- **WHEN** показаны три подсказки, а пользователь разрешает записать только одну
- **THEN** записывается только эта revision в существующий entrypoint, а другие
  подсказки не влияют на flow

#### Scenario: Пользователь просит изменить подсказку
- **WHEN** пользователь просит сократить или переделать предложение, не разрешая
  запись
- **THEN** skill показывает обновлённый дифф и возвращает управление; сохранённый
  файл остаётся byte-for-byte неизменным

#### Scenario: Числом выбрана тема обсуждения
- **WHEN** пользователь отвечает номером варианта, предлагающего обсудить правку
- **THEN** skill обсуждает её без изменения сохранённого файла

#### Scenario: Числом разрешена запись
- **WHEN** показан конкретный дифф и пользователь выбирает номер варианта,
  явно предлагающего записать именно эту правку
- **THEN** skill записывает только эту правку с обычными проверками безопасности

#### Scenario: Разрешение неоднозначно
- **WHEN** ответ не позволяет однозначно определить разрешённую запись
- **THEN** skill уточняет действие без изменения файла

#### Scenario: Последовательные доработки
- **WHEN** после preview или разрешённой записи пользователь просит следующую
  переработку без разрешения записать её
- **THEN** skill показывает новый preview без записи и без нового design scan;
  предыдущее разрешение не распространяется на следующую revision

#### Scenario: База правки изменилась
- **WHEN** перед разрешённой записью чтение обнаруживает изменение файла,
  которое меняет согласованную правку
- **THEN** skill показывает актуальный дифф и запрашивает новое разрешение,
  не перезаписывая файл по устаревшему предложению

#### Scenario: Пользователь пропускает все подсказки
- **WHEN** пользователь не разрешает ни одну предложенную revision
- **THEN** сохранённый flow остаётся byte-for-byte неизменным

#### Scenario: Revision применяется к packaged flow
- **WHEN** одобренная подсказка относится к `<name>/FLOW.md`
- **THEN** skill обновляет этот `FLOW.md` и не создаёт и не переписывает
  `<name>.md`

## ADDED Requirements

### Requirement: Диалог допускает контекстный числовой выбор
`usw-create-flow` SHALL вести диалог по конвенции «Диалог с человеком» из
`openspec/context/08-process-conventions.md`. Skill SHALL сохранять нумерацию
шагов flow в черновике и диффе и contract tokens рецептов.

#### Scenario: Предложен выбор следующего действия
- **WHEN** skill предлагает пользователю выбрать дальнейшее действие
- **THEN** один блок пронумерованных вариантов завершает сообщение, каждый
  вариант объясняет действие, а обозначения в поясняющем тексте не конкурируют
  с номерами ответа

#### Scenario: Пользователь отвечает своими словами
- **WHEN** пользователь словами однозначно выбирает предложенное действие
- **THEN** skill принимает выбор без требования повторить номер или токен

#### Scenario: Требуется самостоятельный ввод
- **WHEN** skill просит сформулировать недостающий текст
- **THEN** вопрос может завершать сообщение без искусственных вариантов ответа
