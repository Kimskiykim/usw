## Context

Мотивация и scope — в [proposal.md](proposal.md). Меняются инструкции модели и
данные eval, без нового runtime. Решения сохраняют text-first и write-safety
из `openspec/context/03-architecture.md` и ADR-001. Design нужен для явного
разделения разрешения записи, границы диалога и ограничений проверки.

## Goals / Non-Goals

**Goals:** сделать разрешаемое действие однозначным и измерить основные
поведенческие границы существующим харнессом.

**Non-Goals:** считать номера строк моделью с гарантированной точностью,
вводить parser диалога или хранить его состояние в handoff.

## Decisions

- Контекстные варианты завершают сообщение одним нумерованным блоком.
  Пояснения используют буквы; нумерация исходного flow внутри диффа сохраняется.
  Свободный текст равноправен номеру. Фиксированное меню снято, поскольку оно
  не различало обсуждение предложения и разрешение конкретной записи.
- Один scan после первоначального сохранения; последующие пользовательские
  доработки продолжают диалог без нового scan. Каждое ожидание ответа возвращает
  управление. При вызове из run-flow действуют его существующие остановка и
  Outcome корня; immutable Markdown исполняемого flow не подменяется.
- Перед каждой разрешённой записью читать актуальный entrypoint и повторять
  проверки безопасности, после — перечитывать результат. Существенно изменённая
  база требует нового preview и разрешения, чтобы не затереть чужую правку.
- Путь, точный контекст и удаляемые строки связывают дифф с файлом. Номера hunk
  не являются критерием; отбрасывать несовпавший контекст по fuzz не предлагается.
- Ранее отклонённые рецепты исключаются до ранжирования scan, в том числе из
  краткого списка. Сведения берутся из текущего диалога, без постоянного реестра.
- В `create-revise-preview` проверять блок `diff`, путь и `equals_flow`.
  Добавить отдельные сценарии числового обсуждения, числовой записи и S3.
  Контекст предыдущего предложения задаётся в input; настоящий multi-turn runner
  не нужен для этого change. Для S3 отдельно просматривать транскрипт.
- Удалить только три отменённых token asserts. В политике тестирования
  различить стабильные токены/структуры и поведение; требование детерминированной
  write-safety сохранить. Якорь на названии раздела не проверяет разрешение.

## Risks / Trade-offs

- Маркеры могут пройти на пустом или неверном диффе → явно указать ограничение
  в notes, вручную проверить транскрипты; `response_diff` отложен.
- `equals_flow` нормализует CRLF/LF → называть результат сравнением текста,
  не доказательством byte-for-byte. Исправление остаётся отдельным backlog item.
- Упоминание отказа может содержать название рецепта → не использовать глобальный
  forbidden marker как семантическую проверку S3; проверять рекомендации вручную.
- Заранее заданные ответы не измеряют реальный многошаговый обмен → обозначить
  границу в notes, не приписывать eval проверку произвольного числа итераций.

## Migration Plan

Коммит A содержит только эти артефакты и delta specs. Коммит B синхронизирует
основную спеку, skill, тест, eval, README и политику. Перед каждым коммитом
проверяется индексируемое состояние: unstaged-изменения убираются через
`git stash push --keep-index`, затем возвращается только созданный stash.
При отсутствии unstaged-изменений проверяемое дерево уже равно индексу.
Откат поведения — отдельный revert коммита B; пользовательские flow не мигрируют.
