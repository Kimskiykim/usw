## Context

Мотив и scope — в `proposal.md`. `run_flow.py` безопасно разрешает entrypoint
и уже возвращает `flow_directory`. Вторая ветка CLI `resource` заново разрешает
entrypoint, читает соседний файл, создаёт отдельную identity и кладёт байты в
JSON как base64. Она закреплена в трёх действующих спецификациях и части тестов.
`03-architecture.md` и глоссарий тоже обещают immutable пакетные ресурсы.

## Goals / Non-Goals

**Goals:** один путь разрешения самого flow, обычное чтение файлов по мере
необходимости, меньше CLI и инструкций, сохранение поведения flat flow.

**Non-Goals:** менять write-safety, identity entrypoint, handoff или выбор
local/shared. Создание другого слоя защиты файлов не требуется.

## Decisions

### Соседние файлы читает агент

Resolver возвращает тот же абсолютный `flow_directory`. У packaged
`<name>/FLOW.md` ссылка `scripts/check.py` означает файл относительно этого
каталога. Если flow запрашивает его содержимое, агент применяет штатный
инструмент чтения; выполняет скрипт только как отдельное действие в пределах
полномочий. Произвольный input не перепривязывается к package. У flat flow
относительные ссылки остаются workspace-relative, как сейчас.

Альтернатива «вернуть UTF-8 вместо base64» сохраняла бы отдельную команду,
повторную загрузку и идентичность ресурса. Она не отвечает запросу владельца
о простом чтении файлов. Новый custom loader также не нужен.

### Удалить протокол `resource` целиком

В `skills/usw-run-flow/scripts/run_flow.py` удалить команду `resource`,
`FlowResource`, `resolve_flow_resource` и привязанные к ним проверки,
кодирование и JSON-поля. `resolve`, `inspect`, `prepare-write` и `write`
сохраняют прежние вызовы и контракты. Оставить `flow_directory` в root и
nested invocation. Ревизия `SKILL.md` и `references/execution-model.md`
убирает команды декодирования, перечитывания и `stale_flow_resource`.

Код safe-access остаётся для entrypoint и записи. При чистке проверить
фактических вызывающих функций: вспомогательный код, используемый другими
ветками, не удалять. Тесты resolver и записи не ослаблять.

### Источник инструкций и граница полномочий

Полный Markdown выбранного flow и его origin/identity сохраняются как прежде.
Модель читает файлы по шагам, когда их действительно требует процесс. Сам
текст flow не разрешает commit, push, deploy или выполнение скрипта; действуют
обычные правила инструмента и платформы. `flow_directory` — контекст
относительной ссылки, не разрешение на чтение или запись.

## Risks / Trade-offs

- Соседний файл может измениться между выбором `FLOW.md` и чтением агентом →
  identity flow по-прежнему относится только к entrypoint. Не утверждать,
  что resource и flow образуют один неизменяемый snapshot.
- Обычные инструменты могут следовать symlink или читать за пределами пакета →
  это теперь поведение хоста и его разрешений; не обещать прежние package
  гарантии, сохранить независимые проверки безопасности самого entrypoint.
- Прямые пользователи команды `resource` получат ошибку неизвестной команды →
  отметить breaking change в README и заменить инструкцию на обычное чтение.
- Разные клиенты по-разному показывают бинарные файлы → использовать
  предоставленные клиентом средства и не обещать универсального текстового
  представления.

## Migration Plan

Коммит A — planning artifacts и проверка strict. Коммит B — delta specs,
context/glossary, CLI, skill, tests и README после проверки на индексе. Живой
behavior eval проверяет чтение packaged файла обычным инструментом и отсутствие
автоматического исполнения скрипта. Затем verify/sync/archive в отдельном
коммите. Существующие flow и раскладки не мигрируют; установленный пакет
обновляется отдельным действием после принятия реализации.

Перед любым коммитом учитывать уже изменённый `skills/usw-find-flow/SKILL.md`
и незакоммиченный `add-flow-skill-frontmatter`: это чужие для данного change
файлы, и stash-verify должен сохранить их без перезаписи.
