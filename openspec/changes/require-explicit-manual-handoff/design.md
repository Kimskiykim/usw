# Активация ручного handoff

## Context

См. `proposal.md`. В handoff metadata нет явной activation policy, а description
описывает только возможность. Runner уже вызывает Begin/Outcome по конфигурации.

## Goals / Non-Goals

Отделить ручную активацию от служебного вызова, сохранив текущий lifecycle.
Не передавать признаки пользовательского намерения в Python и не менять finder.

## Decisions

- Установить `allow_implicit_invocation: false` и явный description триггера.
- Проверять активацию в начале SKILL.md, до конфигурации и state reads.
  Прямой вызов может быть командой, именем skill или просьбой использовать handoff.
- Командные prompts явно привязать к handoff, чтобы их descriptions не выглядели
  общим механизмом сохранения/продолжения. Служебные вызовы runner оставить.
- Python gate отвергнут: CLI не знает намерения человека, а его обязательный
  флаг потребовал бы изменения каждого служебного caller без пользы.
- Проверить native policy детерминированно; добавить behavior scenarios для
  общей просьбы сохранить/продолжить и прямого вызова при отключённом handoff.
- Для отрицательных activation scenarios добавить optional boolean
  `explicit_invocation: false`: вводная harness представляет candidate skill,
  а не имитирует уже разрешённый вызов. Default `true` сохраняет старые сценарии.

## Risks / Trade-offs

Следование тексту зависит от модели → фиксировать отдельно manifest policy,
наблюдение модели и пределы проверки. Evals с file expectations видят записи,
но не доказывают отсутствие чтения; для последнего нужен журнал инструментов.

## Migration Plan

Синхронизировать main spec, обновить исходники и штатно обновлять установленный
skill при установке. Формат и пользовательское состояние не меняются.
