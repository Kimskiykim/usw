## Purpose

Определяет подготовку согласованного OpenSpec change из intent по полному
контракту выбранной схемы без запуска реализации.

## ADDED Requirements

### Requirement: Контракт компонентов определяется выбранной схемой
Flow SHALL получать корень change, полный состав компонентов, их пути,
зависимости и инструкции из OpenSpec CLI. Имя схемы MUST NOT ограничивать
проверки; фиксированный список файлов MUST NOT подменять контракт CLI.

#### Scenario: Схема отличается от spec-driven
- **WHEN** схема использует другие имена, пути и количество компонентов
- **THEN** flow проверяет именно этот состав, не требует отсутствующие в схеме
  proposal/design/tasks и не создаёт их самовольно

#### Scenario: Компонент содержит несколько файлов
- **WHEN** путь компонента является glob и разрешается в несколько файлов
- **THEN** все соответствующие файлы включены в проверку

### Requirement: Неполный контракт не считается успешной проверкой
Flow MUST NOT продолжать ревью при ошибке получения контракта, отсутствии
обязательного компонента или недоступности его содержимого. Пропуск SHALL иметь
основание в статусе `skipped` или условных инструкциях компонента; готовность
одного apply-компонента MUST NOT заменять проверку полного состава схемы.

#### Scenario: Отсутствует delta spec
- **WHEN** spec-driven требует specs, но нужный delta spec отсутствует
- **THEN** отсутствие обнаруживается даже при существующем tasks-компоненте

#### Scenario: Схема явно разрешает пропуск
- **WHEN** CLI пометил компонент skipped или его условные инструкции неприменимы
- **THEN** flow фиксирует основание и не требует создавать этот компонент

#### Scenario: CLI недоступен
- **WHEN** получить состав или инструкции компонентов не удалось
- **THEN** flow возвращает blocked с причиной, не выдумывает пути и не объявляет успех

### Requirement: Проверки учитывают назначение каждого компонента
Flow SHALL проверять содержимое по инструкциям компонента. Разбиение на малые
проверяемые шаги SHALL применяться к компонентам задач по их назначению;
отсутствие такой роли SHALL фиксироваться как неприменимость проверки задач,
без создания дополнительного файла вне схемы.

#### Scenario: План задач переименован
- **WHEN** инструкции назначают компонент delivery-plan источником задач
- **THEN** flow проверяет его задачи по его пути с Definition of Done и proof
  of completion, не обращаясь к выдуманному tasks.md

#### Scenario: Схема не содержит задач
- **WHEN** ни один компонент не назначен источником задач
- **THEN** flow сохраняет полный состав схемы и явно сообщает, что разбивка
  задач неприменима

### Requirement: Оба ревью охватывают все компоненты
Intent drift и feasibility SHALL получать полный актуальный перечень
компонентов, инструкции и содержимое всех их файлов. Drift SHALL сопоставлять
intent и decision log с каждым компонентом в обе стороны, а компоненты между
собой с учётом зависимостей. Непроверенная область MUST NOT получать passed,
clean или ok.

#### Scenario: Противоречие находится вне трёх привычных файлов
- **WHEN** дополнительный компонент противоречит intent или зависимости
- **THEN** ревью включает его в scope и сообщает конкретное расхождение

#### Scenario: Артефакты исправлены
- **WHEN** openspec-update-change изменил состав или содержимое change
- **THEN** flow заново получает перечень и повторяет обе проверки по всему составу

### Requirement: Результат сохраняет границу planning
Flow SHALL возвращать фактический changeRoot, состав компонентов и результаты
проверок с неприменимыми областями. Flow MUST NOT запускать реализацию change
или считать отсутствие задач доказательством готовности к реализации.

#### Scenario: Planning завершён
- **WHEN** все применимые проверки завершены
- **THEN** пользователь получает фактические пути и вердикты; запуск apply
  остаётся отдельным решением
